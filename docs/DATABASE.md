# Database — Drizzle ORM

The API uses [Drizzle ORM](https://orm.drizzle.team). The **provider is chosen through configuration** and defaults to **SQLite**, so the project starts without any database server.

| `DB_PROVIDER` | Driver | `DATABASE_URL` (example) |
|---------------|--------|--------------------------|
| `sqlite` *(default)* | `@libsql/client` | `file:./data/ember.db` (default), `:memory:`, or a Turso URL `libsql://…` |
| `postgres` | `pg` | `postgres://ember:ember@localhost:5432/ember` |
| `mysql` | `mysql2` | `mysql://ember:ember@localhost:3306/ember` |

Only the driver of the selected provider is loaded: imports are dynamic in `database.factory.ts`.

## Switching provider

In `apps/api/.env`:

```dotenv
DB_PROVIDER=postgres
DATABASE_URL=postgres://ember:ember@localhost:5432/ember
```

With Docker Compose, Postgres and MySQL services are ready behind profiles:

```bash
docker compose up --build                                   # SQLite (api-data volume)
DB_PROVIDER=postgres DATABASE_URL=postgres://ember:ember@postgres:5432/ember \
  docker compose --profile postgres up --build
DB_PROVIDER=mysql DATABASE_URL=mysql://ember:ember@mysql:3306/ember \
  docker compose --profile mysql up --build
```

## How it works

```
src/core/database/
├── database.constants.ts   # DATABASE token, list of providers
├── database.types.ts       # DatabaseConnection { provider, db, schema, migrate, close }
├── database.factory.ts     # createDatabase(): opens the connection for the selected provider
├── database.module.ts      # global module: connection + migrations at boot + shutdown
└── schemas/
    ├── sqlite/   index.ts, item.schema.ts
    ├── postgres/ index.ts, item.schema.ts
    └── mysql/    index.ts, item.schema.ts
```

- Drizzle schemas depend on the dialect, hence **one folder per provider**. All three define the same tables, columns and JS types.
- Repositories inject `@Inject(DATABASE)` and only use the query-builder subset shared by the three dialects. They do not use `.returning()`, which MySQL does not support: rows are read back after writes.
- **Ids** are **UUID v7**, generated by the application (`common/utils/uuid.util.ts`). They sort by creation time, which keeps pagination stable even for rows created within the same millisecond.
- **Dates** (`createdAt`, `updatedAt`) are generated by the application, for identical behaviour on the three providers.

## Migrations

SQL migrations are **generated** by `drizzle-kit` into `apps/api/drizzle/<provider>/` and **committed**.
They are applied automatically at boot when `DB_AUTO_MIGRATE=true` (the default).

```bash
# After changing a schema: generate for the 3 providers
MIGRATION_NAME=add_product bun run db:generate:all

# A single provider
DB_PROVIDER=postgres bun run db:generate

# Apply by hand (when DB_AUTO_MIGRATE=false)
DB_PROVIDER=postgres DATABASE_URL=postgres://… bun run db:migrate

# Browse the data
bun run db:studio
```

> Always change the **three** schemas together, then regenerate for the three providers. Otherwise they drift apart.

## Tests

- `test/utils/test-database.ts` provides an **in-memory SQLite** database and an **in-memory Postgres** database ([PGlite](https://pglite.dev), WebAssembly), migrated for each test.
- Repository specs run on both (`describe.each`), which also checks the Postgres migrations without a server.
- E2E tests use `DB_PROVIDER=sqlite` and `DATABASE_URL=:memory:` (`vitest.config.e2e.ts`).

## Keeping a single provider

If your project will never use MySQL, for example:

1. Delete `schemas/mysql/`, `drizzle/mysql/` and the `case 'mysql'` of `database.factory.ts`.
2. Remove `mysql` from `DATABASE_PROVIDERS` and from `drizzle.config.ts`, then uninstall `mysql2`.
